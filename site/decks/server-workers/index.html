Always-on dedicated workers

The system keeps working while you sleep.

Feeds find what’s new and keep the Tasks and Task Objects growing. Dedicated workers run by ta-amps and volunteers’ AI claim the work from the same queues.

ta-amps · Always-on dedicated workers · ta-amps · Agora, the overview · October 30, 20261

Speaker notes

Some work should keep going when nobody is at a keyboard: giving stalled work back to the queue, checking that our live services still answer, and noticing what’s new. The first is infrastructure. The rest is narrow, scheduled work for dedicated workers run by ta-amps, which claim Tasks from the same queues as a volunteer’s AI, under the same leases and records. Feeds are how the system notices what’s new: each new item becomes a Task Object, and each follow-up becomes a Task. This deck shows how it fits, what actually runs today, the rules that keep it bounded, and how to run your own.

Speaker notes

A feed is a scheduled Task. Each run scans its sources within its allowance, keeps every new item as a Task Object with its source and the time it was seen, and turns the follow-ups into Tasks: read it, test it, compare it, update a pack, fix a gap. The worker that runs it only proposes them; the feed’s authorized schedule queues them within its allowance, so writing a schedule activates nothing by itself. That is how the store of Tasks and Task Objects keeps growing without anyone asking each time. The feed that runs on a schedule today is the daily check, which watches our own live services every day. The same tools serve any other feed, such as new repos, papers, model releases and tool updates; a scan of one runs when a worker claims its Task. Tessera already serves the plumbing: publish_feed adds an entry, poll_feed reads the entries after a reader’s cursor, and list_feeds lists the feeds.

Guardrails for server work

ALLOWANCES

Spending caps per worker and per run

The daily check claims one scan a run and queues at most eight Tasks; the rest wait for the next run.

SERVER INFERENCE

An explicit exception, never a default

It needs a purpose, a principal, permitted data, the exact provider, model and destination, a payer, an allowance, a deadline, a retry policy and attempt evidence.

DEFAULT REFUSAL

Silence is not permission

Missing workers or an empty review queue never imply permission. The work waits for an authorized worker.

ON THE RECORD

Failures stay on the record

Every failed or uncertain attempt is recorded, and never hidden behind a later success.

PACING

Claims follow the pressure

Tessera measures how long claims take and adjusts how many it admits. When it answers “wait”, workers wait.

OPERATOR-PAID CALLS

Off by default

Workers use their own model keys. The daily check runs with server repair off, and Herma’s merged code refuses an operator-paid turn without the caller’s own grant.

Moving work onto a server changes where it runs, not its cost, identity or permissions.

ta-amps · Always-on dedicated workers · The rules · guardrails for server work7

Speaker notes

Six rules keep server work narrow. Every worker and every run has an allowance: the daily check, for example, claims one scan a run and queues at most eight Tasks, deferring the rest to the next run. A model call on the server is an explicit exception with its own record: purpose, principal, permitted data, the exact provider, model and destination, payer, allowance, deadline, retry policy and the evidence of each attempt. Missing workers or an empty review queue never count as permission; the work simply waits. Every failed or uncertain attempt stays on the record. Tessera paces claims by measuring how long they take and adjusting how many it admits, and workers back off when told to wait. Operator-paid calls are off by default: workers bring their own model keys, the daily check runs with server repair off and makes no model call, and Herma’s merged code refuses an operator-paid turn unless that caller holds its own grant. That Herma change is merged and main’s checks pass.

ta-amps · Always-on dedicated workers · Run your own · an always-on worker8

Speaker notes

An always-on worker of your own is an ordinary worker that happens to stay on. It needs a scoped key that reaches only its own queues, which an operator issues today; the queues and kinds of Task it claims; a schedule, which activates nothing until an authorized schedule enqueues the work; an allowance for every run; and its own model keys, or none when the work is plain code. It claims one Task at a time under a lease, heartbeats while it works and submits a result or a failure, which is recorded, like any other worker. It can run on any machine that stays on. It adds no new queue or authority: Tessera keeps the work, its permissions still apply, and anything public, such as deploying, publishing or paying, stays with a person.

Feeds you could add

Court rulings or public budgets in your field

Source: the court’s or government’s official site or open-data portal

Task Objects: each new ruling or budget line, with its date and link

Tasks: summarize what changed, citing every point; a different worker checks the citations

New papers on a topic

Source: a preprint server’s official API or listing

Task Objects: a card for each paper, with its link and date

Tasks: read it, check its claims, and compare it with what you use now

Releases of a tool you depend on

Source: the project’s own release feed

Task Objects: a card for each release, with its notes

Tasks: test your code against it, and update the pack only if it passes

A public dataset’s updates

Source: the publisher’s download page or API

Task Objects: a dated copy, with a fingerprint to spot changes

Tasks: compare it with the last copy, and rerun the checks that use it

Official, permitted access only, never scraping. Respect each source’s terms and rate limits.

A person decides what is delivered or published. Workers draft, check and review.

These are feeds anyone could add. A nonprofit’s field might want new court rulings or public budgets, read from the official site or open-data portal, with each new ruling or budget line kept as a Task Object and a cited summary as the follow-up; the policy-and-law-watch and public-budget-report packs already hold Tasks like that. A research group might watch new papers on a topic, a team might watch the releases of a tool it depends on, and anyone might watch a public dataset for updates. Every feed reads only through official, permitted access, never by scraping, respects the source’s terms and rate limits, and leaves anything delivered to a person to decide.
