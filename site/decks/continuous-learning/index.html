Post-training tuning and continuous learning

The system is built to keep learning after it ships.

Small open models are tuned on checked examples, and a rule fixed before scoring decides whether one replaces its base.

ta-amps · Agora, the overview · October 30, 2026

Speaker notes

This deck is about what happens after a model ships. Training made it, and then it froze: the tools, schemas and failures it meets afterwards never reach its weights. Here the system is built to keep learning. Learners turn execution reports into memory, path statistics and routing advice, and small open models are tuned on checked examples and kept only when they beat their base on a test they never saw, under a rule fixed before scoring. Every result in this deck comes from synthetic tasks, and nothing has been promoted or admitted.

THE FIX

Keep learning after deployment

Tune on checked examples of the job, and keep a tuned model only when it beats its base on a test it never saw, under a rule fixed in advance.

The problem

Speaker notes

Training made the model, and then it froze. The tools, schemas and failures it meets after its release never reach its weights, so the same mistakes repeat. A bigger model isn’t the fix: on the same frozen test, Llama 3.2 3B beat the 1B, 52.0% to 12.0% exact match, but it wrote typed values as strings even more often, in 17.5% of its calls against 8.3%, and strict servers reject those calls. Even Muse Glimmer 30B, unchanged, answered 93.3% of a fresh test exactly right, and 96.7% of its replies were valid JSON. The fix is a loop built to keep learning after deployment, which keeps only what beats the base.

  • Measured Llama 3.2 1B and 3B, unchanged, on the same frozen 150-row test: exact match 12.0% and 52.0%; typed values written as strings in 8.3% and 17.5% of calls. Tessera’s continuous-tuning record: the unchanged base models on the frozen, synthetic tool-call test. A typed value written as a string, such as a quoted number, makes a strict server reject the call. Evidence
  • Measured Muse Glimmer 30B, unchanged, on a fresh 150-row test: exact match 93.3%, valid JSON 96.7%. The base model’s scores in the published run record, on a fresh, synthetic tool-call test whose hashes were registered before scoring. Evidence

The loop

01

Generate examples

→ example batches

02

Curate

→ a training set

03

Freeze a test set

→ frozen tests, hashes first

04

Train an adapter

→ a candidate adapter

05

Evaluate

→ evaluation runs

06

Decide by the rule

→ a decision

07

Reload check

→ a reload record

08

Promote or roll back

→ the champion pointer

Keep only what beats the base.

Each step is a verb an authorized worker claims, and each leaves a noun. Keeping the champion is a valid outcome.

Why and how · the loop

Speaker notes

Read the loop clockwise from the top left. Owned templates generate the examples, so no model writes a row or a label. Curation rejects repeats and anything that looks like a test row. The test set is frozen, and its hashes are recorded before any model sees it. A small adapter trains on top of the base, which never changes, and it stays a candidate. Evaluation scores the candidate, the current champion and the unchanged base on the same rows, and the promotion rule, written before any training, decides. The saved adapter must then reload onto a fresh copy of the base and reply exactly the same. Only then does the champion pointer move. Keeping the champion is a valid outcome, and because every version is kept, rolling back is moving the pointer back. The next round starts from the champion, with new examples aimed at its failures.

Why and how · tests and rules fixed before scoring

Speaker notes

Everything that decides was written down before the results it judges. The frozen test is 150 rows over whole tool families that training never sees, pinned by its hash. Each round also draws fresh rows, and their hashes are recorded before any model sees them. The promotion rule was committed before the first training round, and a test pins it. Fingerprints keep look-alikes of test rows out of training. And the rule has said no to real-looking gains. In Llama 3.2 1B’s round 4, a new strategy lifted the development score from 61.25% to 76.25%, but the frozen test stayed at 50.7%. Llama 3.2 3B’s round 2 scored 79.3% but cut schema validity by 0.025, past its 0.02 limit. Muse Glimmer 30B trained on 63 examples gained 5.3 points on the frozen test, but its 95% interval started at 0.0. All three stayed out.

  • Measured Frozen test: 150 rows over tool families held out of training. Tessera’s continuous-tuning record: the test split holds the buckets and feeds tool families, pinned by digest, and training prompts only ever show other families. Each round also freezes a fresh holdout from the test families. Evidence
  • Measured Llama 3.2 1B, round 4: schema-augmented training lifted the development score from 61.25% to 76.25%, but the frozen test stayed at 50.7%; kept out. The development set and the frozen test disagreed. The augmented adapter tied the champion on the test, while its schema validity fell to 61.7% and its false refusals rose to 17.5%, so the rule kept the champion. Evidence
  • Measured Llama 3.2 3B, round 2: 79.3% exact match, but schema validity fell 0.025 against a 0.02 limit; kept out. The adapter scored above the champion, but the promotion rule, committed before any training round, allows schema validity to drop by at most 0.02, so the champion stayed. Evidence
  • Measured Muse Glimmer 30B with 63 training examples: +5.3 points on the frozen test, 95% CI 0.0 to +11.3; kept out. The 63-row run on the frozen development test: exact match 87.3% to 92.7%, with 14 rows better and 6 worse. The paired bootstrap lower bound was not above zero, so the rule kept the base. Evidence

What we measured · Llama 3.2 1B and 3B, synthetic tasks

Speaker notes

Two small Llama models, the same frozen, synthetic 150-row test and the same loop on one local GPU. The 1B went from 12.0% to 43.3% in round 1 and to 50.7% in round 3. Rounds 2 and 4 did not beat the champion, so the rule kept it. Round 1 gained 31.3 points, with a 95% interval of 22.0 to 40.7, and round 3 gained 7.3, with 0.7 to 14.7. The 3B went from 52.0% to 72.7% in round 1, a gain of 20.7 points with 12.0 to 29.3. Its round 2 scored 79.3% but was kept out by a schema guard. The first 63 owned examples were enough to stop the 1B writing typed values as strings, and its type correctness rose from 37.5% to 94.2%. Each configuration ran once, with one seed.

Learners: memory, paths and routing

Not all learning changes a model. Learner runs are ordinary verbs: they read execution reports and write their advice as versioned nouns.

MEMORY

Similar past work

Each run is fingerprinted. Before new work, recall finds similar past runs and how they went, failures included.

memory · minhash-lsh

PATHS

What succeeds

Runs are grouped by category, template, phrasing and shim into scorecards. They show associations, not causes.

path_statistics · wilson-grouping

ROUTING

Which way to try

Weights suggest a shim, method, harness or model, keep exploring the others, and move only with enough evidence.

routing_weights · beta-bandit

MODEL WEIGHTS

The third layer: tuning on real runs

It needs opted-in, verified, rights-cleared runs. That export is designed, not built yet.

Advice only: never a permission, never a hidden agent. The learners are implemented and tested, but not yet shown to improve real work.

How it runs · learners

Speaker notes

Not all learning changes a model. Learners are ordinary verbs that read execution reports and write versioned nouns. Memory fingerprints each run, so before new work an agent can recall similar past runs and how they went, failures included. Path statistics group runs into scorecards of what succeeds; they show associations, not causes. Routing weights suggest which shim, method, harness or model to try, keep exploring the alternatives, and move only with enough evidence. Their outputs are advice, never a permission. Changing model weights from real runs is the third layer: it needs opted-in, verified, rights-cleared runs, and that export is designed but not built, so today’s tuning uses synthetic examples. The learners pass their tests, but they haven’t yet been shown to improve real work.

  • Measured Memory, path-statistics and routing-weights learners: implemented and tested. Tessera’s execution-learning record. Local tests are not evidence that any learner improves real work; that needs the evaluations each learner names, on real permitted runs. Evidence
  • Planned Tuning on opted-in, verified, rights-cleared real runs. The training export is a proposed design in Tessera’s execution-learning record. Nothing exports data from real runs yet. Evidence

Safety and rollback

A round that fails any check leaves the champion where it was.

FROZEN TESTS

Held-out tool families

Training never sees the test’s tools, and every test set is pinned by its hash.

PRE-REGISTRATION

Hashes before scores

The rule and each fresh test are recorded before any model is scored on them.

CONTAMINATION CHECKS

No look-alikes

Fingerprints reject a training row that matches a test row, its request or its template.

RELOAD EQUIVALENCE

It must reload the same

The saved adapter, loaded onto a fresh copy of the base, must reproduce its replies exactly.

A RULE FIXED IN ADVANCE

Beat the base, break nothing

A gain whose lower bound is above zero, and no drop in valid output, refusals or general skills.

ROLLBACK

One pointer, every version kept

Adapters are never overwritten. Promotion moves one pointer, so rolling back moves it back.

Promotion changes no deployment, publication, admission or serving. Privacy is checked too: another key tried to read everything the 1B rounds wrote, and all 303 reads were denied.

How it runs · safety and rollback

Speaker notes

These rules keep the loop honest. Tests are frozen, held out by whole tool families and pinned by hash. The promotion rule and each fresh test are recorded before scoring. Fingerprints keep look-alikes of test rows out of training. A saved adapter must reload onto a fresh copy of the base and reply exactly the same. The rule asks for a real gain, with a lower bound above zero, and no drop in valid output, refusals or general skills. Because adapters are never overwritten and the champion is one pointer that keeps every version, rolling back is moving that pointer back. Promotion here changes no deployment, publication, admission or serving. Privacy is checked as well: after the 1B rounds, a second key tried to read all 303 records, blob chunks and runs they wrote, and every read was denied.

  • Measured Another key tried to read everything the 1B rounds wrote: all 303 reads were denied. A final sweep after the 1B rounds: another principal tried to read 115 private records, 133 blob chunks and 55 execution runs. After the 3B rounds, all 193 such reads were denied too. Evidence

Limits: what we don’t claim yet

  • Everything is synthetic, with one task per result: typed tool calls for Tessera’s own tools.
  • Each configuration ran once, with one seed, so nothing measures the spread between runs.
  • The 150-row tests are small: they can miss a real gain of a few points.
  • Nothing learns from live traffic yet. Rounds start on demand, and exporting real runs for training is designed, not built.
  • Adapter weights aren’t published, and nothing has been promoted or admitted.
  • The learners pass their tests, but haven’t yet been shown to improve real work.

Every kept-out round and every failure stays on the record.

Honest limits

Speaker notes

These are the limits. Every result is synthetic and comes from one task, typed tool calls for Tessera’s own tools, so it says nothing about other tasks or real traffic. Each configuration ran once, with one seed. The tests are small, so a real gain of a few points can be missed. Nothing learns from live traffic yet: rounds start on demand, and exporting real runs for training is designed but not built. The adapter weights aren’t published, and nothing has been promoted or admitted; a promotion here moved only a private pointer. The learners pass their tests but haven’t yet been shown to improve real work. Every kept-out round and every failure stays on the record.

  • Measured The 150-row tests are small. Tessera’s continuous-tuning record: with the disagreement these runs showed, a 150-row test detects a true 5-point gain only about 31% of the time, and 80% power needs about 560 rows. Evidence
  • Planned Learning from live traffic. Rounds start on demand today. A schedule that only enqueues the tick verb, and the export of real runs for training, are designed, not built. Evidence
