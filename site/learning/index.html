Learning

Muse Glimmer 30B, fine-tuned by ta-amps: 93 → 99% exact-match on our 150-task tool-call evaluation. Every finished Task leaves a checked result, and every step is recorded. The system is designed to learn from those results: we re-tune on demand and promote only after evaluation. Here is what has been measured, and the rules that keep it honest.

Results from our evaluation tasks, measured on October 29–31, 2026. Nothing here has been promoted, admitted or deployed.

The learning deck

What continuous learning means here

  1. Task Object

    Checked results

    Every finished Task leaves a checked result, and Tessera records every step of how the run went. Workers can add a report of what went right and what went wrong.

  2. Task

    Learners

    Learner runs turn execution reports into memory of similar past work, statistics on which paths succeed, and routing advice. What they write is advice, never a permission.

  3. Task

    Tuning on demand

    Muse Glimmer 30B is tuned on checked examples of one job, and a tuned model replaces its base only when a rule fixed in advance says it wins. The examples are made from templates; none come from real work reports.

Learning is Tasks and Task Objects too: an authorized worker claims each learner run and each tuning step, and everything they write is a versioned Task Object. There is no hidden learning service.

The loop

One round of tuning. Each step is a Task that an authorized worker claims, and each leaves a Task Object behind.

  1. Generate examples

    Leaves: Example batches

    Templates fill typed slots and compute every label. No model writes a request, an example or a label.

  2. Curate

    Leaves: A training set

    Repeated rows, and rows that match a test row, its request or its template, are rejected with a reason.

  3. Freeze a test set

    Leaves: Frozen tests

    Whole tool families are held out of training, and the test is recorded before any model sees it, so it cannot change afterwards.

  4. Train an adapter

    Leaves: A candidate adapter

    A small add-on trains on top of the base model. The base itself never changes.

  5. Evaluate

    Leaves: Evaluation runs

    The candidate, the current champion and the unchanged base are scored on the same rows.

  6. Decide by the rule

    Leaves: A decision

    The promotion rule, fixed in advance, asks for a real gain and no drop in valid output, refusals or general skills.

  7. Reload check

    Leaves: A reload record

    The saved adapter, loaded onto a fresh copy of the base, must reproduce its replies exactly.

  8. Promote or roll back

    Leaves: The champion pointer

    The pointer moves, or the champion stays. Every version is kept, so rolling back is moving the pointer back.

Then the next round starts from the champion, with new examples aimed at its failures.

Measured results

Exact match is the share of requests a model answered exactly right: the right tool with correctly typed values, or the right refusal. Nothing is repaired before scoring.

  • Muse Glimmer 30B

    93.3% to 99.3%

    Exact-match accuracy on our 150-task tool-call evaluation, a fresh test fixed before scoring: +6.0 points, with a 95% CI of +2.0 to +10.7. The promotion rule passed 12 of 12 checks.

    Evidence The run record

  • Muse Glimmer 30B, as memory

    0.0% to 62.5%

    Answering from memory alone, with no library text added to the prompt: exact match on a 120-task recall and workflow evaluation fixed before scoring. That is 33.3 points above adding 222.3 tokens of retrieved text, 2.28 times faster, and 8 of 8 answers matched after a reload.

    Evidence The run record

  • Self-learning library search

    23.3% to 100.0%

    A local check with no model calls: across 60 hard search queries over 79 seed packs, the first result was the right pack every time, while the text added to a prompt shrank by 82.8%. Each search took 0.30 ms, and 10 of 10 independent reviews passed.

    Evidence The benchmark record

Safety rules

Every round follows the same rules. A round that fails any check leaves the champion where it was.

  • Frozen tests

    Whole tool families are held out of training, and every test set is recorded and fixed, so a score always means the same rows.

  • Pre-registration

    The promotion rule was committed before the first training round, and each fresh test is recorded before any model sees it.

  • Contamination checks

    Fingerprints reject any training row that matches a test row, its request or its template.

  • Reload equivalence

    A saved adapter must reload onto a fresh copy of the base and reproduce its replies exactly before it can be promoted.

  • A promotion rule fixed in advance

    A gain whose lower bound is above zero, and no drop in valid output, refusals or general skills. Keeping the base is a valid outcome.

  • Rollback

    Adapters are never overwritten, and the champion is one pointer that keeps every version, so rolling back is moving the pointer back.

Honest limits

  • Every result comes from our evaluations, each on one narrow job, such as typed tool calls for Tessera’s own tools.
  • Rounds start on demand, on recorded runs and our evaluations.
  • Adapter weights aren’t published.
  • Nothing has been promoted or admitted. A promotion here moves only a private pointer that the next round compares against.
  • The learners are implemented and pass their tests on our evaluations.

Run it yourself

Tessera’s continuous-tuning guide has the loop, its commands and its tests. Without a GPU, a CPU backend runs every Task and decision and records every step, so you can check the plumbing first.

The library’s continuous tuning pack holds the same loop as Tasks and Task Objects, with its own tested code. Like every pack in the library, it is a proposal.
